# Research notes: PS TV 1080p (facts established so far)

## 1. The user's plugin `1080p_480phook.skprx` (2164 bytes, 2023-07-16) — fully reversed
- Fake SELF wrapping a 3-segment ELF (text 0x8420, bss 0x4010, SCE relocs). Module name `ds4vita` (built from xerpi's ds4vita template), version 1.1, kernel module, no exports besides module_start/stop.
- Imports: taihenForKernel {taiHookFunctionExportForKernel 0x45CCFFC0, taiHookReleaseForKernel 0xD22678CA}, SceSysclibForDriver {strlen, memcpy, memset}, SceIofilemgrForDriver {ksceIoOpen, ksceIoWrite, ksceIoClose, ksceIoMkdir}.
- module_start: `uid = taiHookFunctionExportForKernel(KERNEL_PID, &ref, "SceAVConfig", 0x79E0F03F /*SceAVConfig user lib*/, 0x4D37F036 /*sceAVConfigHdmiSetResolution*/, hook); return uid<0 ? SCE_KERNEL_START_FAILED : SUCCESS`.
- hook(int mode, ...): `if (mode == 0x8300) mode = 0x8710; return TAI_CONTINUE(orig, mode, ...)`.
- module_stop: taiHookReleaseForKernel(uid, ref).
- The log_reset/log_write/log_flush functions (ux0:dump/ds4vita_log.txt) are dead leftovers from the ds4vita template; never called.
- Ancestor: https://github.com/gameblabla/1080p_pstv (branch `simp`, 2022-07-05). gameblabla's version forces 0x8710 for ANY mode (`pInput = 0x8710` unconditionally). README: "The PSTV hdmi encoder supports 1080p30 but it was never officially added... overriding the 480p mode and outputting 1080p30 instead. Downside: framerate is halved, some FreeSync monitors don't support it. Upside: 2x integer scale and progressive scan." "Now if you switch to any video mode in the settings, it will switch to 1080p 30." TODO: "Add a check." The user's binary is that TODO done (only remap 480p).
- The user has forked it: https://github.com/delon5/1080p_pstv (default branch `simp`).

## 2. Screen-mode codes (from wiki.henkaku.xyz/vita/SceDisplay, `SceDisplayScreenModeFlag`)
```
0x0000 60 Hz    0x0010 UNK_10 (30 Hz per gameblabla's "1080p30")   0x0020 24 Hz   0x0040 UNK_40   0x0080 50 Hz
0x0300 480P   0x0400 576P   0x0500 1080I   0x0600 720P   0x0700 1080P   0x8000 "standard mode" flag
```
So: 480p60 = 0x8300, 576p50 = 0x8480?, 1080i60 = 0x8500, 720p60 = 0x8600, 1080p60 = 0x8700 (NOT expected to work: HDMI encoder/pixel clock), 1080p30 = 0x8710, 1080p24 = 0x8720 (untested).
- `sceDisplayGetOutputModeForDriver(SceDisplayHead head, SceDisplayScreenMode *pScreenMode, SceDisplayPixelFormat *pPixelformat)` = ksceDisplayGetOutputMode (NID 0xD2CED235, in libSceDisplayForDriver_stub.a, NOT declared in psp2kern/display.h — declare manually).
- `sceDisplaySetOutputModeForDriver(head, screenMode, pixelformat)` = ksceDisplaySetOutputMode (0xAF5EE5BE). Probably only the display-controller side; the HDMI transmitter is set up by SceHdmi `sceHdmiSetupTxForDriver(SceHdmiSetupTxParam*)` (screenMode = "internal VIC, translated to CEA-861 VIC"). sceAVConfigHdmiSetResolution(mode) is the high-level function that does everything; it is a USER export (syscall) of the kernel module SceAVConfig (os0:kd/av_config.skprx), library SceAVConfig NID 0x79E0F03F, function NID 0x4D37F036. Signature: `int sceAVConfigHdmiSetResolution(int screenMode)`.
- Heads: SCE_DISPLAY_HEAD_MAIN_LCD_OLED = 0, SCE_DISPLAY_HEAD_HDMI = 1. `ksceDisplayGetPrimaryHead()` exists. `ksceDisplayGetRefreshRateInternal(int head, float *pFps, int *pScanMode)` (0x7911958E) exists in the stub lib (declare manually; toolchain is softfp so avoid passing floats by value across module boundaries; pointer is fine).
- SceAVConfigForDriver (kernel lib 0xECC77DDB) has 6 unnamed functions (0x0E60701A, 0x2A2E9042, 0x3817CDA1, 0x5662E799, 0x91792D6F, 0xD8B7AE3D) — semantics unknown, do not use.
- User-side SceAVConfig lib also has sceAVConfigHdmiGetMonitorInfo 0x1DD86805 (0xF4-byte EDID-derived struct, flags undocumented), sceAVConfigHdmiSetRgbRangeMode 0x67E1A494, sceAVConfigHdmiGetOutScalingRatio 0x5910A9CB, sceAVConfigHdmiSetOutScalingRatio 0x0DE7CEAB, sceAVConfigChangeReg 0xD0595CE4.

## 3. Registry (decoded registry.db0 dump, FW 3.57 era)
- `/CONFIG/DISPLAY/hdmi_resolution_mode` : int, size 4, default 0. Format line `/11/115/117=0:4:1:32:0:0:30:30:0:0:0:0:1:0:1:0:`. Possible values 0/1/2 presumably map to 480p/720p/1080i in SOME order — mapping unknown (index -> screen-mode code is done by Sony code, probably SceSystemSettingsCore and/or SceShell/av_config at boot).
- `/CONFIG/DISPLAY/hdmi_out_scaling_ratio` : int default 1000000000 (base) / 950000000 (REG-BAS_D = PS TV).
- `/CONFIG/DISPLAY/rgb_range_mode`, `color_space_mode`, `brightness`, `dimming_interval`; `/CONFIG/SYSTEM/hdmi_use_cec`.
- Kernel API: ksceRegMgrGetKeyInt(const char *category, const char *name, int *buf) / ksceRegMgrSetKeyInt (SceRegMgrForDriver). User: sceRegMgrGetKeyInt / sceRegMgrSetKeyInt (SceRegMgr lib 0xC436F916, NIDs 0x16DDF3DC / 0xD72EA399), sceRegMgrGetKeysInfo 0x58421DD1, GetKeyStr 0xE188382F, SetKeyStr 0x41D320C5.
- DESIGN DECISION: never write an unknown value into Sony's key (avoid any chance of a boot loop in av_config/SceShell). Keep "1080p selected" in our own state.

## 4. How the Settings app UI can be extended (HENkaku plugin/user.c, MIT-ish reference; SKGleba/ineedsettings; TheFloW SettingsPlus)
- Settings app = title NPXS10015, main module "SceSettings" (vs0:app/NPXS10015/eboot.bin). It loads "SceSystemSettingsCore" (vs0:app/NPXS10015/system_settings_core.suprx) via sceKernelLoadStartModule. UI pages are XML layouts loaded via `int scePafMiscLoadXmlLayout(int a1, void *xml_buf, int xml_size, int a4)` — import in module "SceSettings", library ScePafMisc NID 0x3D643CE8, func NID 0x19FE55A8. HENkaku hooks it with `taiHookFunctionImport(&ref, "SceSettings", 0x3D643CE8, 0x19FE55A8, patched)` and substitutes the buffer for the top-level page (detected by `strncmp(xml_buf+82, "system_settings_plugin", 22)`), i.e. the XML text begins with `<?xml version="1.0" encoding="utf-8"?>\n<system_settings version="1.0" plugin="system_settings_plugin">` (there is a UTF-8 BOM at the start in the repo file).
- The top-level list links sub pages by file name: sound_settings.xml (title msg_sound_display — this is "Sound & Display", where the PS TV HDMI resolution list lives), network_settings.xml, theme_settings.xml, console_info.xml, etc.
- XML vocabulary (from henkaku_settings.xml): `<setting_list id title icon>`, `<toggle_switch id key title icon hint>`, `<text_field id title icon key keyboard_type max_length>`, `<list id title icon key="/CONFIG/...">` containing `<list_item id title value="0"/>`, `<button id title icon success_dialog_message error_dialog_message>`, `<link id file title icon>`, `<spacer id/>`. Values are bound to registry keys by the framework: the framework calls sceRegMgrGetKeyInt(category, name, &v) / sceRegMgrSetKeyInt(category, name, v) from SceSystemSettingsCore (HENkaku hooks those imports in "SceSystemSettingsCore" to fake its /CONFIG/HENKAKU keys). Category passed is like "/CONFIG/HENKAKU" (HENkaku compares with strncmp(category, "/CONFIG/HENKAKU", 15)).
- Text: `title="msg_xxx"` resolved through `wchar_t *scePafToplevelGetText(void *arg, char **msg)` (import in "SceSystemSettingsCore", ScePafToplevel NID 0x4D9A9DD0, func NID 0x19CEFDA7); HENkaku hooks it and returns its own UTF-16 strings for its msg ids (compiled with -fshort-wchar). Sony's own XML also contains literal titles (e.g. "Sandbox Settings").
- Other hooks HENkaku installs in SceSettings: sceKernelLoadStartModule (SceLibKernel 0xCAE9ACE6, 0x2DCC4AFA) to catch system_settings_core.suprx load, sceKernelStopUnloadModule (SceModulemgr 0xEAED1616, 0x5182E212?? -- check: HENkaku uses 0x2415F8A4 for StopUnload in SceLibKernel 0xCAE9ACE6) and scePafToplevelInitPluginFunctions (ScePafToplevel 0x4D9A9DD0, 0xF5354FEF) for button callbacks.
- SettingsPlus (TheFloW) dumps the XML buffers to ux0: and reads replacements; it used strncmp(xml_buf + 0x52, "system_settings_plugin") (no BOM offset). Detect our page by searching the buffer for the substring `hdmi_resolution_mode` instead of fixed offsets.
- The user's taiHEN config already loads henkaku.suprx under *NPXS10015 and *NPXS10016; our settings plugin is added under *NPXS10015 alongside it (taiHEN chains multiple hooks on the same import fine).

## 5. Framecapper (Rinnegatamante, user plugin, GPL) — what it does
- Hooks in the game's main module (TAI_MAIN_MODULE, TAI_ANY_LIBRARY) the SceDisplay imports: sceDisplayWaitVblankStartMulti 0xDD0A13B8, sceDisplayWaitVblankStart 0x5795E898, sceDisplayWaitVblankStartMultiCB 0x05F27764, sceDisplayWaitVblankStartCB 0x78B41B92; forces the interval to VSYNC_INTERVAL (2 = 30 fps, 3 = 20 fps at 60 Hz). "Inject" variant also hooks sceDisplaySetFrameBuf 0x7A410B64 (user wrapper NID; the raw syscall export is _sceDisplaySetFrameBuf 0xF51523CB) and waits VSYNC_INTERVAL after each SetFrameBuf. The user runs "Framecapper60Inject" (custom build) under *ALL.
- Problem the user hit: at 1080p30 the vblank is 30 Hz, so a game (or Framecapper) waiting 2 vblanks runs at 15 fps. Requirement: frame pacing must be refresh-rate aware so 30 fps titles stay at 30 fps under 30 Hz output.
- SceDisplay user lib NID 0x5ED8F994; also sceDisplayWaitSetFrameBufMulti 0x7D9864A8, sceDisplayWaitSetFrameBufMultiCB 0x3E796EF5, sceDisplayWaitSetFrameBuf 0x9423560C, sceDisplayWaitSetFrameBufCB 0x814C90AF, sceDisplayGetRefreshRate 0xA08CA60D. Kernel: ksceDisplayWaitVblankStartMulti / MultiCB / Internal variants exist in SceDisplayForDriver.

## 7. Hardware test results (PS TV, FW 3.60, 2026-09-11)
- Settings page `sound_settings_plugin` (2711 bytes, dumped): `<list id="resolution" key="/CONFIG/DISPLAY/hdmi_resolution_mode">` with items value 0 = msg_automatic, 2 = msg_720p, 1 = msg_1080i, 3 = msg_480p (also rgb_range 0/1/2, dimming_interval 300/900/1800/0). Our injected item took value 4 (3 was in use).
- Order of operations when the user picks an entry: SceSystemSettingsCore (or the shell on its behalf) calls sceAVConfigHdmiSetResolution(code) FIRST, then the framework calls sceRegMgrSetKeyInt. Codes seen: 0x8300 for 480p; 0x10000000 for a value the core does not know (our 4) -> driver switches to 0x8600 (720p), i.e. 0x10000000 = "automatic". SceSystemSettingsCore does NOT import sceAVConfigHdmiSetResolution (taiHookFunctionImport there fails with 0x90010002); the call comes from another module of the Settings process.
- sceAVConfigHdmiSetResolution(0x8710) from the kernel worker thread: returns 0x80010058 (SCE_ERROR_ERRNO_ENOSYS) every time. The same call issued inside a user-process syscall (Settings app via our SetMode1080p, or SceShell via the v1.1 SetFrameBuf/vblank-wait hook trigger) returns 0 and ksceDisplayGetOutputMode(1) then reports 0x8710. Boot timeline (v1.1): module start 3.0 s, shell pid 5.8 s, apply scheduled 8.8 s, EFFECTIVE at 8.95 s.
- All 7 (v1.1) / 12 (v1.2) SceDisplay user-export hooks install (hooks_ok = 0xFF / 0x1FFF); v1.4 adds two more (expected hooks_ok = 0x7FFF, not yet confirmed on hardware). ksceDisplayGetRefreshRateInternal reports 59.94 for 480p/720p and also for 0x8710 (so it is NOT a reliable 30 Hz indicator; mode flag 0x10 is).
- User report after v1.1: with the plugin replacing Framecapper60Inject, some games flicker or do not hold 30 fps at 1080p30 -> games without any vsync wait of their own; v1.2 adaptive inject addresses that.

## 8. Game reports after v1.2 (2026-09-11)
- Most games fine at 1080p30 with SCALE + adaptive inject.
- Bloodstained: Curse of the Moon: half speed with vsync (30 waits/s -> 30 logic frames/s), double speed with novsync (unthrottled, no own limiter) -> logic advanced once per vblank wait. Needs 2 logic frames per 30 Hz vblank = frameskip (alternate immediate return / real wait).
- Ys VIII: half speed -> same family; may measure elapsed frames via sceDisplayGetVcount deltas (SCALE cannot fix that), so frameskip also scales the reported vcount x2 with 16-bit wrap.
- ksceDisplayGetRefreshRateInternal reports 59.94 at 0x8710, so games asking the refresh rate believe 60 Hz (which is why frame-locked games do not adapt by themselves).

## 9. Tales of Hearts R (PCSE00429) investigation (2026-09-11)
- Crashes with C2-12828-1 under 1080p30 (with any override incl. spoof720 of v1.4), runs under 720p with everything installed. In every 1.3/1.4 boot there is NO process: line for PCSE00429 while other apps get one -> either it crashes before its first call to any hooked display function, or it hit a stale per-process entry (pid reuse) -> v1.4.1 adds process-exit invalidation and hooks sceDisplayGetRefreshRate (0xA08CA60D) as an earlier tracking point. The kernel-side ksceDisplayGetRefreshRateInternal(1) reports 59.94 at 0x8710, but the user-facing sceDisplayGetRefreshRate has not been observed yet (v1.4.1 logs its bits for spoof720 titles).
- Settings-core flow re-confirmed: selecting 720p while our item is active -> SetResolution(0x8600) arrives first (substituted to 0x8710 while mode_1080p=1), then SetKeyInt(2) -> SetMode1080p(0) -> revert to 0x8600. Sony's registry then holds 2 (720p), and the next boot applies 1080p30 from 0x8600.

## 10. Sharpscale dependency (2026-09-11)
- With sharpscale.skprx disabled the console no longer came up in 1080p30 at boot, and selecting 1080p in Settings gave no video at all; re-enabling Sharpscale restores it. The 1080p30 head therefore needs Sharpscale's framebuffer scaling on this setup; the stock display path does not produce a usable picture in 0x8710. Consequence: a "1080p without Sharpscale" bisect is not possible; Sharpscale-related tests must be done through its own settings (scaling mode, framebuffer unlock), not by unloading it.
